# 有限步专家分配检查

## 这个检查回答什么

ProMoE 在每个专家层里，会把每个图像小块交给一位专家。这个检查想回答一个很具体的问题：某次交换在当前一步看起来更好，继续去噪几步以后是否仍然更好。

检查会选两个原本属于不同专家的图像小块，交换它们使用的专家。这样每位专家收到的图像小块数量完全不变，每个图像小块仍只调用一位专家，实际调用量也不变。交换只发生在一个专家层、一个去噪步。完成这一计算后，后续步骤全部恢复模型自己的分配方式。

程序比较四个位置：交换后的第 1、2、4、8 个采样步。第 1 步应当与当前去噪误差给出的排序一致；这是数学和实现检查。第 8 步用于判断当前最优的交换是否会在后续轨迹中变差。

## 它不能证明什么

- 它测量的是两个图像小块一起交换后的效果，不能写成单个图像小块的独立因果作用。
- 它使用冻结模型和真实图像 latent，不是从头训练结果。
- 它不生成五万张图片，不能代替 FID、IS 或正式定性结果。
- 它只在交换发生的那一步严格保持每位专家的负载。后续恢复原生路由后，交换造成的状态变化可能让后续负载发生变化，这正是要观察的传播过程。
- 它只使用 CFG 1.0。真实图像与固定噪声之间有明确的中间状态，可以逐步计算误差；CFG 1.5 没有同样直接的中间真值。正式生成评估仍必须同时报告 CFG 1.0 和 1.5。

## 固定设置

| 项目 | 设置 |
| --- | --- |
| 采样器 | 与 `sample.py` 相同的 250 步 FlowMatch Euler；采样序列 shift 和调度器 shift 都固定为 1.0，并使用同样的 float32 步长 |
| 起点 | 采样下标 50、125、200，对应噪声比例 0.8、0.5、0.2 |
| 后续步数 | 1、2、4、8 |
| 专家层 | Base 模型全部 6 个专家层：1、3、5、7、9、11 |
| 候选 | 每个位置事先按固定随机种子选择 16 个两-token交换 |
| 分配权重 | 每个 token 保留自己原来的 top-1 权重，只改变专家编号 |
| 数值对照 | 原生副本、强制原生副本、每个候选同批次的原生配对副本 |

候选在看到去噪结果前确定，不能先试完再挑看起来最好的交换进入确认集。

## 单个样本运行

```bash
/home/dev/miniforge3/envs/promoe/bin/python \
  analyses/run_finite_horizon_routing_probe.py \
  --ckpt /path/to/ckpt_step_300000.pth \
  --latent /home/dev/imagenet-1k/sd-vae-ft-mse_Latents_256img_npz/<synset>/<file>.latent.npz \
  --label 0 \
  --device cuda:0
```

默认结果写入 checkpoint 对应的：

```text
sample/step<step>/finite_horizon_routing_probe/probe_seed<seed>.json
```

已有文件不会被静默覆盖。确实需要重算时必须显式加入 `--overwrite`。
如果用 `--weights-ckpt` 指向 SSD 上的权重副本，程序会比较完整文件的 SHA256；副本与原文件只要有一个字节不同就拒绝运行。即使不使用副本，程序也不会直接相信协议里写下的哈希：它会对真正交给 `torch.load` 的同一个打开文件在加载前后各算一次 SHA256。latent 也按同样方式检查，程序读取的是哪一个文件，结果就记录哪一个文件的完整哈希；读取期间文件被替换或改写会立即失败。分析固定读取 EMA 权重，不接受普通训练权重代替。

## 主要数字怎样理解

- `immediate_future_spearman`：当前排序和未来排序有多一致。接近 1 表示没必要引入长程信用；接近 0 或为负才说明问题可能存在。
- `sign_disagreement.rate`：当前判断“有益”但未来“有害”，或当前“有害”但未来“有益”的候选比例。
- `top_quartile_overlap`：当前最好的四分之一候选，有多少仍在未来最好的四分之一中。
- `immediate_best_future_regret`：按当前一步挑出的最好候选，比真正的未来最好候选差多少。
- `mean_route_divergence`：一次交换以后，后续各专家层有多少 token 改变了原生专家编号。

真正的门槛由数值安全检查和按图像聚类的置信区间组成。候选标签置换只用来帮助理解“两个排序的配对是否比随机更强”，不进入通过与否的判断，因为它不能正确检验这里关心的“两个排序是否错位”。单个 JSON 只能检查程序和观察个例。
